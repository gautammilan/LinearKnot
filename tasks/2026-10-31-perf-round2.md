# Performance round 2, 2026-10-31 (final, 2026-11-01): `rfv_key` memo and a table `log_add`

Two independent jobs on top of the round-1 `perf/merged` (`6e8e3dc`, binary `bin/dp03_merged`,
md5 `6222c11e886f3b037854192354045eef`).

- **Job A** (`perf/rfv-evict`): memoize the pass-3 v-sweep `rfv_key`, and **drop the table whenever
  the step index changes**, so no entry outlives the step that can use it. Exact by construction --
  the cached double is the one the uncached code computes, and every counter it feeds is replayed.

- **Job B** (`perf/fast-lse`): a tabulated `log_add` behind `-DLK_FAST_LSE`. Approximate on
  purpose (fixed error bound below), separate branch, **not merged**.

Nothing changed what the default build prints: every step was required to reproduce the baseline's
stdout bit for bit before it was kept.

## 1. Job A: the `rfv_key` memo

`rfv_key(ls, p, seed, q, xs)` is the v-sweep's inner sum: walk the closings of `(ls, p, q)` and
add `w_c + V(c.x, c.y)` at `xs`. It was rebuilt on every call. A probe build with counters
(temporary, reverted) on RP150 1-150 measured what that costs:

| metric | value |
| --- | --- |
| calls | 4,172,122 |
| distinct `(ls, seed, p, q, xs)` keys | 521,535 |
| hit rate of a keyed cache | 87.5 % |
| distinct closings keys | 21,667 |

So each closings list was rebuilt about 192 times on average. The result of a call is a pure
function of `(ls, seed, p, q, xs)` -- the closings read `E, cap, dz, pair_bonus, pr_ml_close,
stem_ml_span` and, for `rs`, `Qm[c-1]` with `c-1 < q`, a column already filled and pruned earlier
in the same inside sweep; `prMu` is pass-2 and read-only here. The slow path (`prVkey`, the
log-space list itself) was not touched.

The probe also answered the question that decides the design: every one of the 521,535 distinct keys
was recomputed once behind the cache's back and compared with the stored value -- zero disagreed
(`bad5 = 0`). So the cache replays a stored double and is exact, not merely close. What is cached is
`s` plus the per-kind miss counts of the `mu_at` calls the sum made (`k1` map full, `k2` map not
full, `k3` no map); a hit replays those into `vm_i/vm_ii/vm_iii[ST_U]` and the
`rfv_miss`/`rfv_part_u`/`rfv_key0_u` increments, so `[vmiss]` and `[vmiss3]` print what the
uncached build printed. The key is `key3(p, 2q + seed, xs)` (packs `p < 2^22`, `2q + seed < 2^22`,
`xs < 2^21`, i.e. n <= 1 << 20; the memo is off above that).

Two guards, both value-neutral:

- 200,000-call warmup: a memo whose hit rate is under 25 % after that is dropped and not refilled.
  Uncapped runs (`tests/identity_check.sh`, `--bV 1e7`) do keep their reuse -- 3.65M hits over the
  same 521K entries -- but a lazy G read that is not cut asks each key once, and there the table is
  a random access per call for nothing.
- 16M entries per map: a memory backstop for long inputs (about 550 MB per map, so 1.1 GB for the
  two).

Cache size and hit rate, `[stage] rfvmemo` (new stderr line, numbers from the timing runs):

| case | entries | hits | miss | approx MB |
| --- | --- | --- | --- | --- |
| RP150 1-150 lazy | 521,535 | 3,650,587 | 521,535 | 16.9 |
| Ther 1-349 lazy | 2,747,403 | 11,990,760 | 2,747,403 | 89.1 |

Identity, `bin/dp03_rfvmemo` (md5 `260a6a641dc4894ac5611e3e9e928fc9`) against `bin/dp03_mbase`:

- b1 identical (1571 stdout lines), b2 identical (1571), b3 identical (1194), b4 identical --
  `V pairs`, `G-states`, `G-lazy` all `ok (<= 1e-9)` at `max_rel` 7.8e-13 / 7.4e-13 / 5.7e-13.
- `logZ` equal to the last digit: 116.28132370133829 (b2), 327.39782368482275 (b3).

### 1.1 The follow-up that made the memo free: drop the table when the step changes

The table above is the *uncapped* memo, and the reason this job needed a follow-up: at n = 1000 it
held 29,074,193 entries and 942.7 MB, costing +18.9 % peak RSS. But the live set is one step.
`q` is part of the key (`cpp/pass2/reads_v.hpp:216`) and the only caller passes the step `j`
(`cpp/pass3/scan_prune.hpp:92`), which runs upwards once per step (`cpp/pass3/scan_driver.hpp:25`),
so **no lookup can reach an entry written at another step**. Clearing the two maps when the step
index moves (`cpp/pass2/reads_v.hpp:219-229`, the clears themselves at `:226-227`) therefore cannot
change a returned value -- and it does not lose a hit either: hits are identical to the uncapped
build on RP150 and Ther (3,650,587 and 11,990,760) and *higher* on HXB2 (124,568,940 against
122,212,512, i.e. 80.87 % against 79.34 %), because the uncapped build was refusing inserts at its
16 M cap there; the live set falls to at most 9,359 / 14,690 / 51,947 entries -- 1.1 MB at n = 1000
against 942.7 MB. `clear()` keeps the bucket array and the value blocks, so a step reuses its
predecessor's
memory instead of reallocating. `refused 0` in every case: the 16 M cap is now out of reach, which
makes that backstop dormant rather than load-bearing, and peak RSS against base is +0.0 to +0.3 %
(section 3) instead of +18.9 % (-16.2 % against the uncapped build on HXB2). Two counters were added
to make the peak observable (`cpp/pass2/reads_v.hpp:274-278`) and two fields to the report line
(`cpp/cli/run_report.hpp:69-74`). The 200,000-call / 25 % gate stays (`cpp/pass2/reads_v.hpp:279-284`):
it guards a different failure mode, a no-reuse input, and with eviction in place what it protects is
one step's worth of entries rather than a whole run's.

This is the commit `8ff92a6` on `perf/rfv-evict` (2 files, +31/-10) -- the commit section 8 merges.


## 2. Job B: a tabulated `log_add` (`-DLK_FAST_LSE`)

`log_add` is one inline function in `cpp/common/logspace.hpp` with 212 call sites, so it is the
single choke point for every log-sum in the index. Its slow path is `a + log1p(exp(d))` with
`d = b - a <= 0` -- two libm calls (40-70 cycles together) -- after two early outs that return `a`
when the correction is under the spacing of `a`. Nothing else on the hot path calls a
transcendental: the `std::exp` calls in `g_accum`/`growth_lazy`/`v_build` sit on the log-to-linear
boundary of a beam sum (per node, not per pair), and `stemidx::lse` in `cpp/common/stem_est.hpp` is
a separate self-contained header with its own `NEG_INF`; both were left exact.

`cpp/common/fast_lse.hpp` tabulates the correction instead:

- grid `d` in `[-40, 0]`, step `h = 1/256`, `N = 10240` intervals, `N + 2` doubles (80 KB, built on
  first use, L2 resident);
- linear interpolation between the two grid points around `d`: one multiply, one int convert, two
  loads, one multiply-add;
- `d <= -40` returns `a` (the correction there is 4.2e-18, under the spacing of any log weight);
- `NEG_INF`, the `a < NEG_INF/2` early out, the skip path and NaN are unchanged: NaN keeps the
  exact `log1p(exp(d))` branch, so the documented slow-path behaviour for it is preserved.

Error: linear interpolation of a convex function lies above the curve by at most
`h^2/8 * max|f''|`, and `f'' = e^d/(1+e^d)^2 <= 1/4`, so `(1/256)^2/8/4 = 4.77e-7` per call.
Measured over 40,000,001 points on `[-40, 0]` (`/tmp/test_lse.cpp`, built with `-fsanitize=address`):
`max |err| 4.768e-07 at d = -0.001953`, mean signed `+1.59e-08`. The chord is above the curve, so
the error is one-sided, but it averages to a third of a part in ten million. Endpoints are exact
(`d = 0` gives `0.69314718055994529` to the last digit) and the interpolation never reads out of the
array, including at `d = 0`. The bound quoted in the plan, `h^2/8 = 1.9e-6`, is this bound without
the `f''` factor.

The default build is untouched, verified two ways:

- `g++ -E -P cpp/main.cpp` on the pristine `perf/merged` tree and on the patched tree produce
  identical output (78,079 lines both).
- Default build of the patched tree: md5 `6222c11e886f3b037854192354045eef` -- the round-1
  `bin/dp03_merged`. With `-DLK_FINE_TIMERS` only, md5 `de560b82812ab562c142363d83949606` -- the
  baseline binary of this pass, byte for byte.

`bin/dp03_fastlse` (`-DLK_FAST_LSE -DLK_FINE_TIMERS`) is md5 `a9e3a2c87f80b96e2e5414da8869cb34`.

## 4. Accuracy — T6: the bias of `-DLK_FAST_LSE`

Measured on the *same* 20 runs, by comparing the `.out` files of the four builds of section 3, so this
needed no `dp03` run and no node. `fast` vs `base` is the approximation's own error; `both` vs `fast`
isolates the memo.

| case | log Z Δ | log Z rel | bpp rel max | bpp rel med | bpp abs max | bpp rel max, p > 1e-2 |
| --- | --- | --- | --- | --- | --- | --- |
| RP150 1-150 | +4.322e-06 | 3.717e-08 | 2.383e-06 | 6.543e-07 | 7.075e-07 | 1.776e-06 |
| Ther 1-349 | +6.533e-06 | 1.996e-08 | 2.563e-06 | 5.713e-07 | 6.185e-07 | 2.392e-06 |
| HXB2 1-1000 | +2.547e-05 | 4.120e-08 | 1.423e-05 | 1.107e-06 | 9.473e-07 | 7.368e-06 |

HXB2's 1.4e-05 relative only looks large because HXB2 reports pairs down to 1e-5; the **absolute**
error never exceeds **9.5e-07** on any pair of any case, and log Z is stable to 2–4e-08 relative.
Both are three to four orders of magnitude inside the thresholds this pass set (1e-4 for the pair
probabilities, 1e-2 for log Z).

What the approximation does not do: change the pair set. In all 15 comparisons the exact and
approximate runs report the same pairs (`only-exact 0`, `only-approx 0`), so nothing is dropped,
invented or truncated — only the last digits move.

The two changes compose exactly. `both` vs `fast` is **0.000e+00 in log Z and in every pair
probability** on all five case groups, and `rfv` vs `base` likewise: the memo replays stored doubles,
so it is exact by construction, and this confirms it independently of any timing.

**`tests/identity_check.sh` keeps its 1e-9 tolerance for the exact builds; the approximate build
cannot pass it and should not be made to.** The exact `8ff92a6` build passes at `max_rel` 7.8e-13
(V pairs), 7.4e-13 (G states) and 5.7e-13 (G lazy); a `log_add` with a 4.8e-07 one-sided error cannot
meet 1e-9, and the fast build measures 7.3e-07 to 8.5e-07 — exactly that size. So if
`-DLK_FAST_LSE` ever ships as a default, that check needs a 1e-6 tolerance on that build (or the table
refined: `h = 1/1024` gives 3e-8 for 320 KB). That decision is why `perf/fast-lse` is not merged.

## 5. For the paper

**A pass-3 memo with per-step eviction and a tabulated `log_add`, measured on one idle node with
timer-free builds, 20 interleaved runs.** Dropping the `rfv_key` memo table whenever the step index
moves makes the memo exact *and* removes the memory cost that sank its first version: user CPU falls
**7.7 % at 150 nt, 6.6 % at 349 nt and 13.4 % at 1000 nt**, peak RSS changes by at most 0.3 %, and the
output is identical to the last digit. Replacing the `log1p`/`exp` pair in `log_add` with a
10 240-interval table over `[-40, 0]` takes another **23.1 %, 24.5 % and 21.4 %** on the same cases,
and the two combined give **29.3 %, 30.2 % and 33.8 %**, with a reproduction spread of at most 0.27 %
between interleaved reps. The approximation stays inside the error class it was designed for: log Z
moves by 2.0e-08 to 4.1e-08 relative, and pair probabilities by at most 1.4e-05 relative or
**9.5e-07 absolute** — the absolute figure is the length- and probability-independent one, against
thresholds of 1e-2 and 1e-4, with the reported pair set unchanged. The interpolation bound is
`h²/8 · max|f''| = 4.77e-07` per call, one-sided, so 1e-6 is the accuracy class of that build and
1e-9 remains the class of the exact one.

## 6. Corroboration and excluded numbers

Two earlier sets of measurements are kept here because they agree with the headline in direction and
size, but the headline is **not** built on them.

the branch now carries. In particular, the **"Ther regression" that pass suspected — eviction reading
2.3 % *slower* than base — does not exist**: interleaved on an idle node the same change is 6.6 %
faster. That gap was foreign load on cn-v-1, not a property of the code, and its size (26.30 s for a
23.71 s job, +11 %) is the scale of the error a busy node introduces.


## 7. Open items and one caveat

- **The 16-sequence exactness set was not run end to end.** Seven cases cover it: RP150 (lazy and
  states), Ther 349, RNaseP 233, tmRNA 321, RP486 and HXB2 1000, i.e. 150 to 1000 nt, lazy G. The
  remaining nine tmRNAs (321-359 nt) sit inside that range and would not add a regime.
- **The two jobs were combined and measured together** (section 3, the `both` column): the gains
  add, -29.3 / -30.2 / -33.8 %, i.e. the sum of the two minus at most 1.5 points. There is no
  overlap to reclaim, and the memo's own contribution is *larger* on the approximate build than on
  the exact one, so the combination is not merely additive by accident.
- **The merged tip was rebuilt and re-verified** (section 8): `perf/merged` at `8ff92a6` compiles to
  `e38d249167cf69b0b4254db4e5348ef7`, byte-identical to the binary timed in section 3, and passes the
  round-1 b1-b4 harness against the frozen baseline (`RESULT PASS`, log Z 116.28132370877114 /
  116.28132370133829 / 327.39782368482275, `identity_check.sh` at `max_rel` 7.8e-13).
- **Job A's per-call residual is `mu_at` plus the `log_add` chain**, one per closing, and the memo
  touches neither. Going further means caching the whole xs-profile of a closings set the way the
  non-sweep `prVkey` path already does, which is a different data structure (a dense span per
  `(ls, p, q)` instead of one scalar per `xs`), so it was not attempted here.
- **The hit-rate gate is a judgement, not a measured crossover**: 200,000 calls of warmup and a 25 %
  floor. The measured cases sit at 81-88 % hits (87.5 % on RP150, 81.4 % on Ther, 80.9 % on HXB2), so
  the constants are not load-bearing for them; they exist so that a no-reuse input cannot pay for the
  table.
